## Not proven

- **That a second person is refused.** No sign-in with an email outside the policy was tried. The evidence is the configuration only: one Allow policy, with only the owner's emails.
- **A signed-in visit, checked from outside.** The check had no login, so it saw only what someone without one gets. No signed-in visit through the tunnel is part of this record.
- **That the page's reads wake no thread.** The server makes the same reads as `openwiz`, through the same code and allowlist, and `openwiz` woke no idle thread in its rerun. But the server's log has no timestamps, so it cannot show whether the page made any reads during that check.
- **Safari, iPhone and screen readers.** Every browser test ran in Chromium. Nothing was tested in Safari or on iOS, and no real screen reader (such as VoiceOver) was used. The accessibility evidence is automated checks in Chromium only.
- **Performance targets.** There are none yet. The timings in `apps/web/src/timing.ts` are provisional, and the measurements are on fixtures.
- **Paging over a list that changes.** Offset paging can miss a thread, or show one twice, if the list changes between pages. The page says when it sees the count change, but cannot prevent it.
- **Overlapping reads in every case.** The page starts a new read only after the server has answered the last one, or 70 seconds after sending it. If the tunnel delays a request by more than 10 seconds, or a run ignores the core's 30-second budget, two runs could still overlap on the Mac.
- **Cloudflare's real responses.** The tests use synthetic copies of Access's and Cloudflare's answers (login redirect, `401`, error pages). The live check saw the real login redirect only.
- **Everything 0.0.1 did not prove** still applies: see [0.0.1's list](0.0.1-live-check.md#not-proven).

## The live check

**Status: Live observation, one run, on one machine.** It gives the method, the environment, the results as counts, and the limits. It holds no hostname, team name, email, address, session id or title.

### The method

All read-only. The server and the tunnel were already running, and were not changed.

1. **Loopback only (A3).** On the Mac: list the processes listening on the server's port; request the server on the Mac's own network address; request its health route on the loopback address.
2. **No login, no data (A1).** From a machine outside the owner's network: request the page (`/`) and the inventory route (`/api/v1/inventory`) at the public hostname, once with no cookies, and once with a forged `CF_Authorization` cookie (a random string in the shape of a token).
3. **The server's log.** Count its lines by kind, and look for any error.
4. **The binary and the page.** Check the running server's SHA-256, and the page files against the list of SHA-256 values made when they were built.

### The environment

| What | Value |
| --- | --- |
| Machine | A Mac with Apple Silicon (macOS), the maintainer's own, with their real CloudRoom account |
| `room-cli` | v127, as the maintainer reports it |
| `openwiz-server` | Built natively on that Mac with Rust 1.99.1 from the 0.0.2 release line at commit `37b14ce125823d03542a5fdaa97e0c441d19f57f`; SHA-256 `710f79b6ee47e733e17b4aa4547393fbf23e65cb06177cdc65bac7b91397bfff` |
| The page | `apps/web/out` (16 files), built with Node.js 24.22.1 on Linux from the same commit, copied to the Mac, and served with `--web-root` |
| Access | Cloudflare Tunnel (locally managed, Access required at the origin) and an Access application with one-time PIN sign-in and a 24-hour session, set up as in [docs/web-access.md](../web-access.md) |
| When | 2026-10-30, right after the rerun below |

**The checked build and this release.** The checked server was built before an unused part was removed: the code for a later, unreleased message-sending command, which the server never called. Its removal changes the shared CloudRoom adapter that the server is built with, so a server built from this release does not have the checked build's SHA-256. Apart from that removal, comments, and the version number, nothing in the code changed. The page's code is unchanged: built from this release, its scripts, stylesheets and fonts are byte-identical to the checked build's, and its two HTML files differ only in the build id that Next.js picks at random for each build.

### The results

| Check | Result |
| --- | --- |
| **A3: loopback only** | **Pass.** Exactly one listener on the server's port: `openwiz-server`, IPv4, on the loopback address. A request to the Mac's own network address on that port was refused at once (connection refused). The health route on the loopback address answered `200` |
| **A1: no login, no data** | **Pass.** All four requests (page and inventory route; no cookie, and a forged cookie) got the same answer: a `302` redirect to the Access login, with a 143-byte "302 Found" body. No JSON and no page content |
| **The server's log** | **Pass.** 42 lines: 1 start-up line ("loopback only, with the web page"); 40 `GET` requests answered `200` (3 for the page, 20 for its files, 13 for the inventory, 3 for health, 1 for one thread's details); 1 `GET` answered `404`, logged without its path. No line says error, panic, fatal or fail |
| **The binary and the page** | **Pass.** The running server's SHA-256 is the one above. All 16 page files match their recorded SHA-256 values |
| **A2: only the owner gets in** | **Configuration only.** One Allow policy, whose only rules are the owner's own email addresses. No second identity tried |

### Limits, plainly

- **Seen from outside without a login only.** A signed-in session was not checked from outside.
- **No second identity.** Who else Access lets in is known from its configuration, not from a refused sign-in.
- **No timestamps in the server's log,** so the log cannot be lined up with other events.
- **One machine, one account, one run.**
