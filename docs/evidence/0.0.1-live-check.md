# OpenWiz 0.0.1: what was tested, and the live check

Everything 0.0.1 was tested with, what is not proven, and the full record of its one live check. The [changelog](../../CHANGELOG.md) lists what 0.0.1 adds and links here; the dependencies are in [docs/dependencies.md](../dependencies.md).

## What was tested

| Evidence | What it covered | Result |
| --- | --- | --- |
| **Fixture tests** (in this repository) | The 12 proof cases P1 to P12 (coverage, freshness, unknowns, partial failures, paging and the time budget, verified grouping, bounded output, the read-only allowlist, reported configuration, JSON matching the text, visibility, version and schema drift), plus checks on dependencies, fixtures, limits and the JSON schema. They run against a fake `room-cli` with synthetic data | 91 proof tests and 16 checks pass on Linux with Rust 1.99.1. Anyone can rerun them with `cargo test --workspace` |
| **A native build on macOS** | `cargo build --release` on an Apple Silicon Mac with Rust 1.99.1 | Built and ran. The fixture tests last ran there on an earlier 0.0.1 build |
| **One live check, on one Mac, with `room-cli` v127** (2026-10-29) | `ls`, `ls -l`, `show`, a missing-id `show` and a full paged listing against 2,488 real threads, compared before and after a 120-second wait; events and queued messages for 20 samples. Details [below](#the-live-check) | **Passed:** no idle thread changed; no sample gained an event or a queued message; P1, P4 and P6 consistent; all 46 OpenWiz runs exited as expected, and none of its 305 reads was refused |

The live check ran a build from just before the tested-version label was set to `v127`; that label is the only difference in the program's code ([details](#the-environment)). A rerun with the new label is planned. *Updated for 0.0.2:* it was rerun on 0.0.1's final build on 2026-10-30, and passed: [0.0.2's evidence page](0.0.2-live-check.md#001s-live-check-rerun-on-its-final-build).

## Not proven

- **That a read can never wake a thread or mark it read.** The live check found no such effect, but it had [limits](#limits-plainly): no request-level inspection, events for 20 samples only, a 120-second window, only five fields compared, already-busy threads not judged, hidden threads not observed, and its own reads assumed to have no effect.
- **Freshness and unknowns against CloudRoom's own view.** These are fixture-tested only; no live comparison was made.
- **Slow machines and other output.** Whether `thread list` always finishes within the 15-second read limit on a slower machine, whether `room-cli` ever prints anything other than JSON (such as an update notice), and whether it starts helper processes, are all unobserved.
- **Other `room-cli` versions.** Only v127 was checked live. Others run and are shown as untested; a future change in `room-cli`'s output could make fields unknown, which OpenWiz reports as gaps.
- **Other systems.** Windows is untested. Linux has fixture tests only.
- **Anything beyond CloudRoom.** No other service, personal agent or PACP behaviour is part of 0.0.1.

The text output is provisional and may change. The `--json` format is versioned as `openwiz.inventory.v1`.

## The live check

**Status: Live observation, one run, on one machine.** This section is the published evidence for what OpenWiz 0.0.1 claims about real CloudRoom sessions (threads). It gives the method, the rules, the environment, the results as counts, and the limits. It holds no session ids, titles, project or machine names, host names, or account names: the raw before and after lists contain private session data and stay on the machine where the check ran.

**In one sentence:** with `room-cli` v127 on a Mac, OpenWiz 0.0.1's `ls`, `ls -l`, `show` and full paged listing ran against 2,488 real sessions, and in the 120 seconds that followed, no session that was quiet before the check changed in any compared field, and none of 20 sampled sessions gained an event or a queued message.

### What it set out to show

1. **Reads have no visible effect.** Running OpenWiz does not change a quiet session: not its status, its update time, or its read and attention times, and in a sample, not its events or queued messages.
2. **The inventory matches CloudRoom's own lists** (proof cases P1, P4 and P6): every session appears once in every view; a session that does not exist gives an explicit not-found and nothing more; a session is grouped only under a project from the same run's project list.
3. **OpenWiz runs as documented:** every run exits as expected, and it makes only the reads on its allowlist.

It does not set out to show freshness or unknowns against CloudRoom's own view (P2, P3); those are fixture-tested only.

### The method

The check is a read-only script, run once by the maintainer on their own Mac. It calls `room-cli` directly for its own reads, and runs OpenWiz behind a small wrapper that records each `room-cli` call OpenWiz makes and refuses any call outside OpenWiz's allowlist.

1. **Binary.** It verifies the OpenWiz binary's SHA-256 and the commit of its checkout before any read, and stops if either differs.
2. **Version.** It reads `room-cli --version` and records it. The version is never a gate.
3. **Before.** It reads `thread list --json` in all four views (default, `--include-hidden`, `--include-archived`, and both) and keeps, for **every** session in the combined view, five fields: `status`, `runtime.displayStatus`, `updatedAt`, `lastReadAt` and `latestAttentionAt`. It also reads both project lists and the machine list. It then picks **20 sample sessions**: quiet, idle sessions, alternately cloud and local, in OpenWiz's own order. For each sample it reads `thread show` (for the queued-message count) and finds the number of the session's last event.
4. **OpenWiz.** It runs:
   - `openwiz ls` and `openwiz ls -l`;
   - `openwiz show <sample>` for 3 of the samples;
   - `openwiz show <an id that does not exist>`;
   - in each of the four views, `openwiz ls --json --limit 0`, then every page with `--limit 200`;
   - and `room-cli thread count --json` once, for comparison.
5. **Wait 120 seconds.**
6. **After.** It repeats the list reads, and for each sample reads `thread show` again and every event after the number it found before.
7. **Compare and report.** It compares before and after, checks P1, P4 and P6, and prints a report of counts and outcomes only. Before printing, it checks the report against every session, project and machine id it saw, the account name, the host name and the paths, and prints nothing if any of them appears.

### The rules

A session is **quiet** if, before the check, it was idle, with no queued work, no pending interaction and no background activity. Every other session is **already active**.

| Outcome | When |
| --- | --- |
| **Fail** | A quiet session changed in any compared field; a sample gained an event or its queued-message count changed; an OpenWiz run exited other than expected (0, or 3 for the missing id); the wrapper refused a read; or P1, P4 or P6 was inconsistent |
| **Incomplete** | Something could not be compared: a session whose activity could not be read, a sample whose queue count or last event number could not be read (or went down), a row whose id could not be read, a missing compared field, or a quiet session whose rows differ between the list views. Never a pass |
| **Pass** | No failure, nothing incomplete, and P1, P4 and P6 all consistent |

- **Already-active sessions are not judged.** Their changes are reported by field and count, but they cannot be attributed to OpenWiz, because they were working anyway.
- **Excluded:** the two CloudRoom sessions that ran the check itself, given by id. They are reported separately and not judged.
- **Classing is fixed by the before snapshot.** A session quiet before stays judged, however it looks afterwards.

### Limits, plainly

- **No request-level inspection.** The check did not look at the requests `room-cli` sends to CloudRoom. It looked only at what changed afterwards.
- **Events for the samples only.** Event logs and queued messages were compared for the 20 samples. Every other session was compared on its five list fields only.
- **A 120-second window.** An effect slower than that would not show.
- **Fields not compared are unseen.** Only the five list fields above, and, for samples, events and the queued-message count.
- **Observer neutrality is assumed.** The check's own reads are not proven to have no effect; there was no control run without OpenWiz. An effect of the check's reads would have shown up as OpenWiz's, and none showed.
- **Already-active sessions are not judged**, so a read's effect on a session that was busy anyway is unknown.
- **One machine, one account, one run** (plus the earlier run below). Not repeated elsewhere.
- **An earlier run was incomplete.** A first run, 40 minutes earlier on the same day, found no failure, but 3 rows differed between the list views of one snapshot, taken moments apart, so it could not pass. The check was corrected to class such a session by its before-snapshot row, as it already did for changes (a quiet one still blocks a pass), and was run again. This page reports that rerun.
- **What this does not cover:** freshness and unknowns against CloudRoom's own view (P2, P3), how long `thread list` takes on a slower machine, whether `room-cli` ever prints anything other than JSON, and whether it starts helper processes.

Fixture tests for every proof case are in this repository: `cargo test --workspace`. They show the logic; this page is the only live evidence.
