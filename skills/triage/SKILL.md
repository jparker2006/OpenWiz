# Triage

Sort the issues that reach the tracker outside a plan graph, so each one ends with a **brief** an agent could build from, a specific question, or a reason to close it. The labels are Matt Pocock's. The orchestrator runs it, whenever the five-minute check finds triage work and whenever the user asks.

**Sorting starts nothing.** You may mark an issue `ready-for-agent`, but no agent starts on it until the user approves it: it joins a plan graph the user approves, or the user approves it on its own.

## What comes in

| What | How it looks | Go to |
| --- | --- | --- |
| A new issue: a bug or an idea someone filed | Open with no state label, outside any milestone, with no parent issue and no sub-issues; or filed with `needs-triage` | Sort an issue |
| A low finding from a review | A standalone issue, never a sub-issue of the spec, labelled `needs-triage` by `review-ticket`, its body starting `Follow-up of #<ticket> (spec #<spec>)` | Sort an issue |
| A reply to triage | Labelled `needs-triage` or `needs-info`, and someone wrote on it after triage did | Sort an issue, again |
| A builder's question | A ticket labelled `ready-for-agent` and `needs-info`, and its builder wrote on it after triage did | Answer a builder |

Specs and their tickets belong to `plan-graph`, and a ticket being built belongs to its builder. So an issue with no state label that sits in a milestone, has a parent issue or has sub-issues is left alone: it is a spec, or a ticket waiting for its plan graph's approval.

## The labels

Every issue you sort ends with exactly one **category** label and one **state** label. The five state labels are the ones in `docs/agents/triage-labels.md` (the `setup` skill writes it: if it is missing, run `setup` first); if it maps a role to a different label name, use that name everywhere below. In these meanings, the maintainer is the user (you prepare, they decide), and the reporter is whoever filed the issue.

| Label | Means | Who sets it |
| --- | --- | --- |
| `bug` | Something is broken | You |
| `enhancement` | New feature or improvement | You |
| `needs-triage` | Maintainer needs to evaluate this issue | You, or whoever files an issue for sorting (`review-ticket` does, for a low finding) |
| `needs-info` | Waiting on reporter for more information | You, with triage notes; or a builder, on its own ticket |
| `ready-for-agent` | Fully specified, ready for an agent to take unattended | You, once the claim is checked and the brief is posted |
| `ready-for-human` | Requires human implementation | You, with a brief that says why an agent can't do it |
| `wontfix` | Will not be actioned | You, only after the user says yes; then close the issue |

- **The usual path:** a new issue goes to `needs-triage` first, and from there to `needs-info`, `ready-for-agent`, `ready-for-human` or `wontfix`. A `needs-info` issue goes back to `needs-triage` when the reporter replies.
- **A ticket being built keeps its labels.** Its `ready-for-agent` came with its plan graph's approval. On such a ticket, change only `needs-info`, and add no category.
- **Two state labels on any other issue** is a conflict: tell the user, and change nothing on it until they decide.
- **Every comment you post starts with this line,** exactly as Matt wrote it:

  ```
  > *This was generated by AI during triage.*
  ```

  It also marks your comments, which is how `find-work.sh` (below) tells whether anyone has written since you did.
- **Comments hold facts about the work:** no keys, tokens or personal details, and nothing from a chat but the user's decisions, quoted.

## Find the triage work

Run `find-work.sh`, beside this file, from the project's root (in this repository, `sh skills/triage/find-work.sh`). It reads every open issue, 100 at a time, and each one's newest comment, and takes the label names from `docs/agents/triage-labels.md`. It lists the triage work oldest first, one line per issue, `#<number> <what>: <title>`:

| `<what>` | The issue |
| --- | --- |
| `new` | Has no state label, sits in no milestone, and has no parent issue and no sub-issues |
| `to sort` | Has `needs-triage`, and its newest comment is not triage's (or it has none) |
| `reply` | Has `needs-info`, and its newest comment is not triage's |
| `builder question` | Has `needs-info` and `ready-for-agent`, and its newest comment is not triage's |

- **It prints nothing and exits 0** when there is no triage work, so the five-minute check can run it as it is.
- **It exits 2** when it could not read every open issue, or the labels file: it then prints nothing, and says why on stderr. That is a failure, never "nothing to do": run it again, and tell the user if it keeps failing.
- **Its test** runs it against a fake `gh` that serves synthetic issues the way GitHub does: `python3 -I skills/triage/test/test_find_work.py`. Change the script only with its test passing.

The list is for choosing what to read, never evidence: read each issue in full, every comment included, before you decide anything about it. A run is done when the script no longer lists any issue you handled.

## Sort an issue

1. **Read.** The whole issue: its body, every comment, its labels, who filed it and when. Keep what earlier triage notes settled, and never ask again what they answered. Read the glossary and the ADRs (`docs/agents/domain.md` says where they are). For a low finding, also read the review report and the pull request it came from. Then check the code twice:
   - **Already built?** Search for the behaviour by what it does, in the glossary's words, not by the issue's wording. Note where you looked. A low finding may have been fixed since its review, so check it against the default branch.
   - **Rejected before?** Read every file in `.out-of-scope/`, and note any that matches the request by concept ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).

   Done when you can say where you looked, whether it is already built, and whether it was rejected before.
2. **Check the claim.** For a bug, reproduce it from the reporter's steps. For an outside pull request, check it out and run its tests. Run only what the project's rules let you run without asking (its tests and fixtures); for anything that needs the user's machine, their account or a live read, write down what it would take instead. Done when you have one result, and why: **confirmed** (with the code path), **not reproduced**, or **not enough detail to try** (a strong sign of `needs-info`).
3. **Decide.** Pick one category and one state, with your reasons:

   | You found | State | Then |
   | --- | --- | --- |
   | It is clear and checked, and an agent can do it alone | `ready-for-agent` | Post a brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)) |
   | It needs a person: a judgement call, access, a live step or manual testing | `ready-for-human` | Post a brief that also says why an agent can't do it |
   | Facts are missing that someone can give | `needs-info` | Post triage notes (below) |
   | It needs the user's decisions: a design, a trade-off, a change of plan | `needs-triage` | Ask the user (see "Tell the user"). A design too big for a few questions needs a grill: offer one |
   | It is already built | `wontfix`, once the user says yes (`needs-triage` until then) | Ask the user. On yes, say where it lives in a comment, and close it |
   | It matches an earlier rejection, or you would reject it | `wontfix`, once the user says yes (`needs-triage` until then) | Ask the user. On yes, close it as [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) says |

4. **Apply.** Set the labels (one category, the new state, and the old state label removed) and post the comment. Never close an issue without the user's yes. Done when the issue has exactly one category and one state label, and its newest comment is yours, saying what you found and what happens next.

**Triage notes**, for `needs-info`:

```markdown
> *This was generated by AI during triage.*

## Triage notes

**What we know so far:**

- ...

**What we still need from <who can answer>:**

- ...
```

Put everything already settled under "What we know so far", so none of it is lost. Ask whoever can answer: the reporter, or the user when the reporter was an agent that has finished. Each question is specific and answerable ("Which page were you on when it happened?"), never "please provide more info". A question only the user can answer also goes in "Tell the user".

## Answer a builder

A builder that is stuck writes its question on its ticket and adds `needs-info` (`build-ticket`). It waits for the answer.

1. **Read** the question, its ticket, the ticket's spec, the grill behind the spec, the glossary, the ADRs, `docs/agents/`, and the code it asks about.
2. **If one of those settles it,** answer on the ticket: the answer, and where it comes from. Remove `needs-info`, and tell the builder in one line that its answer is on the ticket.
3. **If it needs a decision** none of them settles (a design choice, a change to the plan, anything live), ask the user (see "Tell the user") with your recommendation, and say on the ticket that it is with them. When they answer, post their exact words on the ticket, remove `needs-info`, and tell the builder.
4. **A file outside its owned paths:** add the file to the ticket's owned paths only when no other open ticket owns it, and record the new paths, and why, in a comment on the ticket. When another open ticket owns it, ask the user.

Done when the ticket's newest comment is yours, with the answer or saying it is with the user, and `needs-info` is gone once it is answered.

## Nothing starts without approval

- **A label starts nothing.** `ready-for-agent` means sorted and briefed, not approved. Work starts only when the user approves it, in one of two ways:
  1. **It joins a plan graph:** it becomes part of a spec's plan (`plan-graph`), and the user's approval of that plan graph covers it.
  2. **The user approves it on its own,** in words that name it ("approve #42"). Before you ask, propose its owned paths and what it relies on, read fresh from the code (the brief names no files), so it can be built like any ticket. Then record the approval in a comment on the issue: `**Approved on its own by <user>, <YYYY-MM-DD>:** "<their exact words>"`, with a link to the brief they approved, its owned paths and what it relies on.
- **"Move #42 to `ready-for-agent`" changes a label; it approves nothing.** Apply it (write the brief if there is none), and ask whether they also approve the work.
- **Low findings wait for their spec's closing summary.** There the user approves them together, or drops them; record that approval on the spec issue the way `plan-graph` records a plan graph's, and close each dropped one as `wontfix`. Have each one sorted before then, so it takes them one word.

## Tell the user

- **Only what needs them,** in one message per run, in your own thread. Write each question on its issue too (for a ticket, on its spec issue as well). Give each item the issue, what you found, the decision needed, and your recommendation, worded so that "yes" accepts it.
- **What needs them:** a `wontfix` to confirm, a decision a `needs-triage` issue waits on, a question only they can answer, the approval of a `ready-for-agent` issue (on its own, or as part of the next plan), and each new `ready-for-human` issue. Low findings wait for their spec's closing summary instead.
- **When the user asks what needs their attention,** run `find-work.sh`, and show what it lists grouped by `<what>`, oldest first, with a count and one line each, then what is waiting on them. Let them pick.
- **When the user names an issue,** sort it now, whatever its labels.

## Outside pull requests

When `docs/agents/issue-tracker.md` says outside pull requests count as requests, a pull request from outside the project is an issue with code attached: same labels, same steps, with the `gh pr` commands that file lists. List them with:

```sh
gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER", "MEMBER", "COLLABORATOR") | not) | "#\(.number): \(.title)"'
```

On a pull request, `ready-for-agent` means an agent should take the next step on its code, and the brief says what is left to do; `ready-for-human` means it is ready for a person to merge.
