# Writing a brief

A **brief** is the comment you post on an issue when it moves to `ready-for-agent` (or `ready-for-human`). Once it is posted, the brief is the contract, and the issue's body and discussion are only background. If the user approves the issue, a builder works from the brief.

## What makes a good brief

- **It lasts.** An issue can wait for weeks while the code changes around it. Describe behaviour, interfaces, types and the shape of any setting: names the agent can look for. Leave out file paths and line numbers; they go stale. (Its owned paths are added, read fresh, when the user approves it: see "Nothing starts without approval" in [SKILL.md](SKILL.md).)
- **It says what, not how.** The agent explores the code itself and makes its own choices.
  - Good: "The `SkillConfig` type accepts an optional `schedule` field of type `CronExpression`."
  - Bad: "Open the types file and add a field on line 42."
- **Every acceptance criterion can be checked on its own.**
  - Good: "`gh issue list --label needs-triage` lists only issues that have been through a first sort."
  - Bad: "Triage works correctly."
- **It says how each criterion will be proven:** the test or check that fails first and passes once the work is done.
- **It says what is out of scope,** so the agent doesn't polish what nobody asked for.

## Template

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** one line: what needs to happen

**Current behaviour:**
What happens now. For a bug, the broken behaviour; for an enhancement, what it builds on.

**Desired behaviour:**
What should happen once the work is done, edge cases and errors included.

**Key interfaces:**
- `TypeName`: what changes, and why
- `functionName()`: what it returns now, and what it should return

**Acceptance criteria:**
- [ ] A specific, testable criterion
- [ ] Another

**Proof:**
- The test or check that fails first for each criterion, and passes after

**Out of scope:**
- What this issue does not change
```

- **For `ready-for-human`:** the same shape, plus a **Why a person:** line (a judgement call, access, a live step or manual testing).
- **For an outside pull request:** "Current behaviour" describes the diff as it stands, and the brief says what is left to do to it (finish it, close its gaps, answer its review), not how to build it from nothing.

## Example

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** A long skill description is cut mid-word

**Current behaviour:**
A skill description longer than 1024 characters is cut at exactly 1024
characters, so it can end mid-word ("Use when the user wants to confi").

**Desired behaviour:**
It is cut at the last word boundary before 1024 characters, and ends
with "...".

**Key interfaces:**
- The `SkillMetadata` type's `description` field: no type change, but the
  code that fills it from a SKILL.md's frontmatter keeps whole words

**Acceptance criteria:**
- [ ] A description under 1024 characters is unchanged
- [ ] A longer one is cut at the last word boundary before 1024 characters
- [ ] A cut description ends with "...", and is at most 1024 characters long

**Proof:**
- A test with a 1030-character description fails before the change, and
  passes after

**Out of scope:**
- Changing the 1024-character limit
- Descriptions over several lines
```

A bad brief says "the triage thing is broken, look at the main file around line 150": no category, no current or desired behaviour, paths and line numbers that go stale, nothing to check it against, and no edge to its scope.
